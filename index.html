What Is Version Control?

Version control is a system that records changes to files over time so you can recall specific versions later. It's the backbone of modern software development — and now essential for BI teams.

⏪

Track Changes

Every edit is recorded with who made it, when, and why. Roll back to any previous state instantly — no more "report_v3_FINAL_v2.pbix" files.

🤝

Team Collaboration

Multiple developers can work on the same report simultaneously using branches. Changes are merged with conflict detection and resolution.

🛡️

Disaster Recovery

The entire history lives in a remote repository. Accidental deletions, overwrites, or corrupted files are instantly recoverable.

✅

Code Review

Pull Requests enforce peer review before any change reaches production. Quality gates catch errors before they impact stakeholders.

🔀

Branch Strategy

Develop new features in isolation. Maintain separate dev, test, and prod environments aligned with your release process.

📜

Audit Trail

Complete traceability for compliance. Know exactly what changed in every report version — critical for regulated industries.

// Why It Matters for Power BI
The Problem with .PBIX Files
❌ Without Version Control
  • Email chains of PBIX file attachments
  • No idea who changed what measure last week
  • Overwrites destroy hours of work
  • Can't test changes without breaking production
  • No rollback — you're stuck with broken reports
  • Binary files — impossible to diff or review
✅ With Version Control
  • Single source of truth in a Git repository
  • Every change attributed to a developer
  • Branching protects production reports
  • Automated testing before deployment
  • One-command rollback to any version
  • Text-based PBIP files are fully diffable

The PBIP Format

Power BI Project (.pbip) is a folder-based format that stores your report and semantic model as readable text files — making them compatible with Git version control.

📦 What is PBIP?

PBIP (Power BI Project) is an open, text-based file format introduced by Microsoft to replace the binary .pbix format. Instead of a single opaque binary file, a PBIP project is a folder structure containing JSON and TMDL files that represent every aspect of your report and data model.

⚡ Key Benefits
  • Git-diffable — see exactly what changed line by line
  • Human-readable — open any file in VS Code
  • Merge-friendly — collaborate without conflicts
  • Portable — share logic, not binary blobs
  • CI/CD ready — automate deployments via pipeline
// PBIP Folder Structure
📁 MySalesReport.pbip ← workspace root │ ├── 📁 MySalesReport.Report/ │ ├── report.json ← report metadata │ ├── 📁 pages/ │ │ ├── ReportSection1/ │ │ │ ├── page.json ← page settings │ │ │ └── visuals/ ← visual configs │ └── definition.pbir ← entry point │ ├── 📁 MySalesReport.SemanticModel/ │ ├── definition.pbism ← model definition │ └── 📁 definition/ │ ├── model.bim ← TMDL / tables │ ├── 📁 tables/ │ │ ├── Sales.tmdl │ │ └── Date.tmdl │ └── 📁 measures/ │ └── KPIs.tmdl │ └── .gitignore ← ignore caches

Azure Repos Setup

Azure Repos is Microsoft's cloud Git service, tightly integrated with Power BI. Learn how to configure repositories, set up branch policies, and prepare for workspace integration.

☁️ What is Azure Repos?

Azure Repos is part of Azure DevOps and provides unlimited, cloud-hosted Git repositories with built-in Pull Request workflows, branch policies, and deep integration with Power BI workspaces. Unlike GitHub or GitLab, it's tightly coupled with Microsoft's ecosystem — making it ideal for enterprise Power BI teams.

1

Create an Azure DevOps Organization

▼

Visit dev.azure.com and create a new organization (or use an existing one). This is your central hub for version control, CI/CD pipelines, and team collaboration.

  • Sign in with your Microsoft/Entra ID account
  • Click "Create organization"
  • Name it something meaningful (e.g., MyCompany-Analytics)
  • Choose your region
  • Click "Continue"
2

Create a Project

▼

Projects group your repositories, pipelines, boards, and other resources. Create one specifically for Power BI work.

  • In your organization, click "New project"
  • Name: PowerBI-Analytics (or your preference)
  • Visibility: Choose Private for security
  • Version control: Select Git
  • Click "Create"
3

Create a Git Repository

▼

Inside your project, create a new repository to store your Power BI PBIP files. This is where all your reports and data models will live.

  • Go to Repos → Files
  • Click "New repository"
  • Repository name: SalesReport (or your report name)
  • Check "Initialize with a README"
  • Add .gitignore for C# / .NET (Power BI uses similar exclusions)
  • Click "Create"
4

Initialize the Repository

▼

In your project, go to Repos → Files. Initialize with a README and add a .gitignore for your project type.

BASHCOPY
# Clone the empty repo to your local machine git clone https://dev.azure.com/YOUR_ORG/PowerBI-Analytics/_git/SalesReport cd SalesReport # Copy your PBIP project files into the cloned folder # Then add and commit git add . git commit -m "feat: initial Power BI project setup" git push origin main
5

Configure Branch Policies

▼

Go to Project Settings → Repos → Policies and configure the main branch protection rules.

  • ✅ Require a minimum number of reviewers (set to 1 or 2)
  • ✅ Check for linked work items
  • ✅ Check for comment resolution
  • ✅ Require merge strategy (Squash merge recommended)
  • ✅ Build Validation — run pipeline before merge
📌 Tip

Branch policies prevent anyone (including admins) from pushing directly to main. All changes must go through a Pull Request — this is how you enforce quality gates.

6

Create .gitignore for Power BI

▼

Create a .gitignore file at the root of your repo to exclude Power BI cache and local settings files:

.gitignoreCOPY
# Power BI cache and local files *.pbix .pbi/ # Report cache **/.pbi/ **/localSettings.json # Auto-recovery files *.pbix.autorecovery # OS files .DS_Store Thumbs.db # VS Code .vscode/settings.json
// Module 05
Workspace Git Integration

Connect your Power BI Premium or Microsoft Fabric workspace directly to Azure Repos. This enables bi-directional sync between the workspace and your repository.

⚠️ Prerequisites
  • Workspace must be in Premium Per User (PPU) or Microsoft Fabric capacity
  • Azure DevOps organization must be in the same Azure tenant as your Power BI tenant
  • You must have Admin access to the workspace
  • Git integration must be enabled by the Fabric admin in tenant settings
1

Enable Git Integration in Tenant Settings

▼

As a Fabric Admin: Go to Fabric Admin Portal → Tenant Settings → Integration Settings.

  • Enable "Users can synchronize workspace items with their Git repositories"
  • Enable "Users can export items to Git repositories in other geographical locations" (if needed)
  • Enable for the entire organization or specific security groups
2

Connect Workspace to Azure Repos

▼

In Power BI Service, navigate to your workspace:

  • Click Workspace Settings (gear icon)
  • Go to Git integration tab
  • Select Azure DevOps as the provider
  • Select your Organization, Project, Repository
  • Set the Branch (e.g., main or dev)
  • Set the Git Folder path (root / or subfolder)
  • Click "Connect and sync"
✅ What Happens Next

Power BI will scan the repository folder and import any PBIP-format reports and semantic models found. These appear in your workspace ready to work with.

3

Understand Sync Status Icons

▼

In the workspace, each item shows a Git sync status indicator next to its name:

  • 🟢 Synced — workspace matches the branch
  • 🟡 Uncommitted changes — workspace has local changes not in Git
  • 🔵 Update available — Git has newer commits not yet pulled
  • 🔴 Conflict — workspace and Git diverged, manual resolution needed
4

Branch Strategy for Workspaces

▼

Best practice is to connect each workspace to a different branch, matching your deployment stages:

Dev Workspace → feature/* branch (developer experimentation) Test Workspace → develop branch (QA & validation) Prod Workspace → main branch (production, locked)

This ensures only reviewed, approved code reaches production — enforced by branch policies on main.

// Module 06
Hands-On Project

Build a Sales Analytics Power BI report with full version control from scratch. Follow each step in sequence.

📋 Project Scenario

Your team needs to build a Sales Analytics Dashboard tracking revenue, units sold, and regional performance. You'll use PBIP format, Azure Repos, and implement a complete CI/CD workflow so the whole BI team can collaborate safely.

1

Set Up Git Repository Locally

▼

Clone the Azure Repos repository and set up the project folder structure.

BASHCOPY
# Clone the repo git clone https://dev.azure.com/YOUR_ORG/PowerBI-Analytics/_git/SalesReport cd SalesReport # Create folder structure mkdir Reports SemanticModels Docs git add . git commit -m "chore: initial folder structure" git push
2

Create Feature Branch

▼

Create a feature branch for development. This keeps your work isolated until it's reviewed and approved.

BASHCOPY
# Create and check out a new feature branch git checkout -b feature/sales-dashboard # Now you're on the feature branch # All commits here won't affect main until merged git branch
3

Build Report in Power BI Desktop

▼

Open Power BI Desktop and create your Sales Analytics report. Save it as PBIP format in your local repo folder.

  • Open Power BI Desktop
  • Connect to your Sales data source
  • Create the semantic model with tables, columns, and measures
  • Build report pages with visuals (cards, charts, tables)
  • Go to File → Save As
  • Choose format: Power BI Project (.pbip)
  • Save to: ~/SalesReport/Reports/SalesAnalytics.pbip
4

Commit Changes to Local Git

▼

Add your PBIP files to Git and commit with a descriptive message.

BASHCOPY
# Check status git status # Stage all PBIP files git add Reports/SalesAnalytics.pbip/ # Commit with descriptive message git commit -m "feat: create Sales Analytics dashboard - Added Sales, Date, and Product tables - Created measures: Total Revenue, Units Sold, Avg Price - Built Executive Summary page with KPI cards - Added regional breakdown charts"
5

Push Feature Branch to Azure Repos

▼

Push your commits to the feature branch on Azure Repos.

BASHCOPY
# Push feature branch to remote git push -u origin feature/sales-dashboard # The -u flag sets this as the default upstream branch # Next time, just 'git push' without specifying the branch
6

Create Pull Request in Azure DevOps

▼

Go to Azure DevOps and create a Pull Request to merge your feature branch into main.

  • Go to your Azure DevOps project
  • Click Repos → Pull Requests
  • Click "New Pull Request"
  • Source: feature/sales-dashboard
  • Target: main
  • Add title: Add Sales Analytics Dashboard
  • Add description with context about the changes
  • Click "Create"
7

Request Review from Team

▼

Add reviewers who will check your PBIP file diffs and validate the changes.

  • In the PR, click "Add reviewers"
  • Select colleagues (at least 1-2 required by policy)
  • Add a comment requesting review: "Please review the measure definitions and visual layouts"
  • Reviewers will get notifications and can add comments on specific lines
8

Address Review Feedback

▼

Reviewers may request changes. Make updates in Power BI Desktop and push new commits to the same branch.

  • Make changes locally in Power BI Desktop
  • Commit and push again (PR automatically updates with new commits)
  • Address reviewer comments in the PR thread
  • Once approved, proceed to merge
9

Complete Pull Request (Merge to Main)

▼

After approval, merge the PR into main. This makes your changes official.

  • In Azure DevOps PR view, click "Complete"
  • Merge strategy: Select "Squash commit" (recommended)
  • Check "Delete source branch" (clean up)
  • Click "Complete merge"
  • Your changes are now on main — ready for workspace deployment
10

Workspace Auto-Syncs Changes

▼

The Power BI workspace connected to this repository automatically detects the new commits and shows an "Update available" badge.

  • Go to your Power BI workspace
  • Look for the 🔵 "Update available" badge on items
  • Click "Update all" to pull changes from Git
  • Reports are instantly live for stakeholders!

Complete Developer Workflow

From a developer's first commit through deployment to production workspace — this is the entire CI/CD pipeline visualized and explained step by step.

🔨
STEP 01

Create Feature Branch Locally

Developer creates a feature branch on their local machine to develop in isolation.

What happens here: The developer's local Git repository (already cloned from Azure Repos) now has a new branch. They switch to it and all commits on this branch are separate from the main branch, ensuring other developers aren't affected.

git checkout -b feature/new-kpi-margin # Developer is now on the feature branch # Any commits here stay local until pushed
📊
STEP 02

Make Changes in Power BI Desktop

Developer opens the Power BI report (saved as PBIP), edits measures, adds visuals, and saves locally.

What happens here: Power BI Desktop modifies PBIP files (JSON and TMDL) on disk. The files in the feature branch folder are updated. Git tracking sees the changes but hasn't committed them yet — this is called "Uncommitted Changes" in Git terminology.

# In Power BI Desktop # Add measure: Gross Margin % = DIVIDE([Gross Profit],[Total Revenue]) # Add measure to Executive Summary page card visual # Save (Ctrl+S) # PBIP files on disk are updated automatically
💾
STEP 03

Commit to Git

Stage changed PBIP files and create a descriptive commit with the change summary.

What happens here: The developer reviews the diff (git diff), stages meaningful changes, and writes a commit message following conventional commits format for a clear history.

git add SalesAnalytics.SemanticModel/ git add SalesAnalytics.Report/pages/ExecutiveSummary/ git commit -m "feat(kpi): add Gross Margin % measure to Executive Summary - Added Gross Margin % = DIVIDE([Gross Profit],[Total Revenue]) - Updated Executive Summary page card visual - Linked to story #1042"
⬆️
STEP 04

Push to Azure Repos

Push the feature branch to the remote repository, making changes visible to the team.

What happens here: The feature branch is pushed to Azure Repos. Azure DevOps may automatically trigger a build validation pipeline to run basic checks on the pushed code before a PR can be created.

git push origin feature/new-kpi-margin # Azure DevOps outputs a direct link to create a PR: # remote: Create a pull request for 'feature/new-kpi-margin': # remote: https://dev.azure.com/MYORG/.../pullrequests/new?...
👁️
STEP 05

Pull Request Review

Designated reviewers examine the PBIP file diffs, comment on issues, and approve or request changes.

What happens here: In Azure DevOps PR view, reviewers see a clean diff of every .tmdl and .json file. They can comment on specific lines, request changes, and approve. Branch policies enforce that all required approvals and checks pass before merge is allowed.

# Reviewer checks: measure formula correct? # Reviewer checks: naming conventions followed? # Reviewer checks: no unintended visual changes? # All checks pass → Reviewer approves ✅
🔀
STEP 06

Merge to Main Branch

After approval, the PR is completed and changes are squash-merged into the main branch.

What happens here: The PR is completed via Azure DevOps UI using Squash merge. The main branch now contains the reviewed, approved changes. The feature branch is deleted. The connected workspace will now show a blue "Update available" badge.

# Complete PR via Azure DevOps UI: # Repos → Pull Requests → [Your PR] → Complete # Merge type: Squash commit (keeps main history clean) # ✅ Delete source branch after merging # → main branch is now updated with your changes
🔄
STEP 07

Workspace Sync

The Power BI workspace detects the new commits on main and syncs — making changes live for stakeholders.

What happens here: Since the workspace is already connected to Azure Repos, Power BI Service automatically detects the new commits on the main branch. A workspace member goes to the workspace, sees the blue "Update available" badge, and clicks "Update all" to pull the latest PBIP files and publish the updated reports.

# In Power BI Service: # 1. Open your connected workspace # 2. Look for the 🔵 "Update available" badge on items # 3. Click "Update all" at the top of the workspace # — OR — click the badge on individual items # 4. Power BI pulls latest PBIP from main branch # 5. Reports are live for stakeholders instantly ✅ # No pipeline needed — the Git integration # IS the deployment mechanism!
// How Workspace Sync Works
Workspace Auto-Detects Changes
✅ What Triggers a Sync Notification
  • A PR is merged into the branch your workspace is connected to
  • A direct commit is pushed to that branch (if allowed)
  • The workspace polls Azure Repos and detects new commits
  • A workspace admin manually clicks "Update all"
⚠️ Important Notes
  • Sync does not happen automatically — a workspace user must click "Update all"
  • Only items tracked in the connected Git folder are synced
  • Data refresh schedules and permissions are not stored in Git — manage separately
  • Each workspace connects to exactly one branch at a time
🔄 Multi-Environment Branch Strategy
Dev Workspace → connected to → feature/* or develop branch (developers work here) Test Workspace → connected to → release/* branch (QA validation) Prod Workspace → connected to → main branch (stakeholders view here)

Each workspace admin clicks "Update all" after the relevant PR merges into their branch. No pipeline required — the workspace is your deployment mechanism.
